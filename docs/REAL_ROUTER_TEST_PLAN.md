# خطة ومعايير اختبار الاتصال الحقيقي براوتر MikroTik (Real Router Test Plan)
## منصة Jalsah لإدارة شبكات MikroTik وبطاقات HotSpot

---

### 1. الهدف من الوثيقة (Purpose & Scope)
تهدف هذه الخطة إلى تحديد المعايير الفنية والضوابط الأمنية الصارمة اللازمة لاختبار الاتصال الحقيقي الآمن بجهاز راوتر MikroTik من خلال المسار البرمجي المعتمد، وقراءة المؤشرات التشخيصية المحدودة (`identity`, `resource`, `routerboard`) دون إجراء أي عمليات كتابة أو تعديل على إعدادات الراوتر، ودون المساس ببيانات الإنتاج.

---

### 2. المتطلبات المسبقة القانونية والتشغيلية (Prerequisites & Ownership)
1. **الملكية أو التفويض الصريح**: يُحظر قطعياً توجيه أي اختبار أو استعلام إلى جهاز راوتر لا يملكه المشغّل أو لا يملك إذناً خطياً وتشغيلياً صريحاً بإجراء الاختبارات عليه.
2. **بيئة اختبار معزولة (Staging / Lab Router)**: يُوصى بشدة بإجراء الاختبار الميداني الأول على راوتر معملي تجريبي غير متصل بمشتركين فعليين أو شبكة إنتاجية نشطة.
3. **أخذ نسخة احتياطية (Backup)**: يجب تصدير نسخة احتياطية كاملة من إعدادات الراوتر (`/export file=pre_test_backup` و `/system backup save name=pre_test`) قبل ربطه بالمنظومة.
4. **حظر إدراج الأسرار في Git**: يُحظر بشكل قاطع تسجيل أي عناوين IP حقيقية، أو أرقام تسلسلية خاصة، أو كلمات مرور، أو بصمات شهادات فعلية داخل مستودع الأكواد (Git) أو توثيقاته العامة.

### 3. حساب تشخيصي مقيد الصلاحيات (Least Privilege Diagnostic Account)
لحماية جهاز الراوتر من أي خطأ برمجي أو اختراق، **يُمنع استخدام حساب `admin` الافتراضي منعاً باتاً**. يجب إنشاء حساب فحص مؤقت ومقيد حصرياً بالحد الأدنى من الصلاحيات المطلوبة للقراءة:

#### أ. جدول سياسات الصلاحيات (Permissions Matrix):
| السياسة (Policy) | الحالة | التعليل الأمني |
| :--- | :---: | :--- |
| `api` | **مسموح** | مطلوبة لفتح قناة اتصال بروتوكول RouterOS Binary API. |
| `read` | **مسموح** | مطلوبة لقراءة معلومات النظام والموارد والمعالج وذاكرة الراوتر. |
| `test` | **مسموح** | مطلوبة لتمكين دوال فحص جهوزية النظام وقراءة المؤشرات الحيوية. |
| `write` | **محظور قطعياً** | يمنع إجراء أي تغيير في الإعدادات أو القواعد أو الواجهات. |
| `policy` | **محظور قطعياً** | يمنع تعديل الصلاحيات أو إدارة المستخدمين أو تغيير المجموعات. |
| `password` | **محظور قطعياً** | يمنع تعديل أو قراءة كلمات المرور لحسابات الراوتر الأخرى. |
| `sensitive` | **محظور قطعياً** | يمنع تصدير الشهادات أو المفاتيح الخاصة أو أسرار النظام. |
| `reboot` | **محظور قطعياً** | يمنع إعادة تشغيل الراوتر أو إيقافه برمجياً. |
| `sniff`, `romon`, `ftp`, `ssh`, `telnet` | **محظور قطعياً** | خدمات غير مستخدمة ويجب حجبها عن مستخدم التشخيص. |

#### ب. أوامر التهيئة عبر سطر أوامر MikroTik (RouterOS CLI):
```routeros
# 1. إنشاء مجموعة تشخيصية مقتصرة تماماً على القراءة
/user group add name=jalsah-read-diag policy=api,read,test comment="Jalsah Read-Only Safe Probe Group"

# 2. إنشاء مستخدم مخصص للاختبار بكلمة مرور عشوائية معقدة (لا تُحفظ في المستودع)
/user add name=jalsah_tester group=jalsah-read-diag password="<GENERATE_STRONG_RANDOM_PASSWORD>" comment="Temporary Read-Only Test User"
```

### 4. التمييز الشبكي للراوتر وإمكانية الوصول (Network Topology & Reachability)
يجب التمييز بدقة بين السيناريوهات الشبكية الثلاثة ومعوقات كل منها:

```
+-----------------------------------------------------------------------------------------+
|                                    السيناريوهات الشبكية                                   |
+-----------------------------------------------------------------------------------------+
| [1] راوتر بعنوان عام ثابت/DDNS  <--- (اتصال سحابي مباشر عبر 8729/TLS) <--- الخادم السحابي   |
| [2] راوتر خلف NAT أو CGNAT       <--- (الاتصال المباشر مستحيل!)        <--- الخادم السحابي   |
|     (يتطلب VPN صادر من الراوتر WireGuard/IPsec إلى السيرفر)                               |
| [3] راوتر محلي (LAN 192.168.x.x) <--- (الاتصال المباشر مستحيل!)        <--- الخادم السحابي   |
|     (الخادم السحابي لا يملك مساراً محلياً، ويتطلب نفقاً أو مسار هاتف محلي)                |
+-----------------------------------------------------------------------------------------+
```

#### أ. الراوتر ذو العنوان العام (Public IP / DDNS):
- يملك عنوان IPv4 عام وثابت أو اسم نطاق ديناميكي (مثل MikroTik Cloud DNS: `<SERIAL>.sn.mynetname.net`).
- يستطيع خادم السحابة الاتصال به مباشرة على منفذ `8729` (API-SSL) أو `443` (REST HTTPS).
- **التحدي**: يتطلب تشفيراً آمناً وحماية دقيقة لمنفذ الخدمة من الهجمات العامة.

#### ب. الراوتر خلف شبكة محجوبة (Carrier-Grade NAT / CGNAT أو مزود خدمة مقيد):
- تمنح معظم شركات الاتصالات المتنقلة والألياف الضوئية عناوين ضمن نطاق CGNAT (`100.64.0.0/10`) أو نطاقات خاصة بدون عنوان عام.
- **الحقيقة الفنية**: **الاتصال المباشر الوارد من الخادم السحابي إلى الراوتر في هذه الحالة مستحيل فيزيائياً وشبكياً** لأن الراوتر غير معنون على الإنترنت العام ولا يمكن فتح منافذ واردة إليه.
- **الحل المطلوب**: يجب أن يقوم الراوتر نفسه بإنشاء اتصال صادر عبر نفق مشفر (WireGuard أو SSTP أو OpenVPN أو IPsec) إلى الخادم السحابي، ليصبح معنوناً ضمن شبكة خاصة مصرح بها (`AUTHORIZED_VPN_SUBNETS`).

#### ج. الراوتر على الشبكة المحلية الخاصة (LAN 192.168.x.x / 10.x.x.x):
- يقع الراوتر على شبكة داخلية معزولة عن الإنترنت العام.
- **تأكيد حاسم**: **الخادم السحابي المرفوع على الإنترنت (`https://alrafeerouter.zone.id`) لا يمكنه الوصول برمجياً إلى عناوين الشبكة المحلية (مثل 192.168.88.1)**، ويتم حظر هذه الطلبات برمجياً في `SsrfProtection` لمنع ثغرات SSRF وحماية السيرفر السحابي.

### 5. مخاطر كشف منفذ الإدارة للإنترنت والبدائل الأكثر أماناً (Security Risks & Alternatives)
فتح منفذ إدارة الراوتر (مثل 8729 أو 443) مباشرة على الإنترنت العام يترتب عليه مخاطر أمنية حقيقية:

1. **مخاطر الكشف المباشر (Direct Exposure Risks)**:
   - **هجمات التخمين الآلية (Brute-Force Attacks)**: تفحص أدوات المسح مثل Shodan وCensys الإنترنت باستمرار لمحاولة كسر كلمات مرور منافذ RouterOS.
   - **ثغرات اليوم صفر (Zero-Day Vulnerabilities)**: أي ثغرة في مكتبة TLS أو معالجة الحزم في نظام RouterOS قد تعرض الجهاز للاختراق حتى قبل مصادقة المستخدم.
   - **هجمات حجب الخدمة (DDoS)**: إغراق منفذ الإدارة بطلبات مصافحة TLS يستهلك موارد معالج الراوتر.

2. **البدائل الأكثر أماناً (Recommended Secure Architectures)**:
   - **الخيار الأول (الأعلى أماناً - Authorized VPN Tunnel)**: ربط الراوتر عبر نفق WireGuard أو SSTP آمن بالخادم السحابي، وإغلاق منافذ الإدارة تماماً عن الإنترنت العام وحصرها في واجهة النفق (`AUTHORIZED_VPN_SUBNETS="10.200.0.0/24"`).
   - **الخيار الثاني (تقييد الوصول عبر جدار الحماية - IP Allowlisting)**: إذا تعذر استخدام VPN وكان للراوتر IP عام، يجب حصر الوصول لمنفذ 8729/443 حصرياً بالعنوان العام الصادر لخادم السحابة (Backend Public Egress IP) ورفض بقية العناوين:
     ```routeros
     /ip firewall filter add chain=input protocol=tcp dst-port=8729 src-address=<BACKEND_EGRESS_IP> action=accept comment="Allow Jalsah Cloud Egress Only"
     /ip firewall filter add chain=input protocol=tcp dst-port=8729 action=drop comment="Drop all other API-SSL traffic"
     ```
   - **الخيار الثالث (تغيير المنفذ الافتراضي)**: تجنب استخدام المنافذ الافتراضية المعروفة للمهاجمين، مع الحفاظ على التشفير الكامل.

### 6. التحقق من شهادة TLS وبصمة التشفير (TLS Verification & Pinning)
1. **الشهادات الرسمية الموثوقة**: في حال توفر شهادة موقعة من جهة إصدار معتمدة (مثل Let's Encrypt أو ZeroSSL)، يتم تفعيل `rejectUnauthorized: true` والتحقق من اسم النطاق وشهادة CA.
2. **الشهادات ذاتية التوقيع (Self-Signed Certificates)**:
   - يجب استخراج بصمة SHA-256 للشهادة من داخل الراوتر عبر مسار آمن:
     ```routeros
     /certificate print detail where name="<CERT_NAME>"
     ```
   - تُمرر البصمة المكونة من 64 رمزاً سداسي عشري (Hex) في حقل `certificateFingerprint`.
   - يقوم الخادم بمطابقة البصمة رقمياً (`cert.fingerprint256 === cleanFingerprint`) عبر خاصية Certificate Pinning الصارمة، ولا يُلغى التحقق إلا عند تطابق البصمة كلياً لمنع هجمات الرجل في المنتصف (MITM).

### 7. خطوات تنفيذ اختبار الاتصال (Step-by-Step Diagnostic Execution)

#### المرحلة الأولى: التحقق التحضيري (Pre-Flight Checks)
1. التأكد من هوية الراوتر وصلاحيات المستخدم التشخيصي.
2. التأكد من عمل خدمة `api-ssl` على المنفذ المخصص وربطها بالشهادة الصحيحة.
3. التأكد من إمكانية الوصول الشبكي إلى العنوان الهدف.

#### المرحلة الثانية: تنفيذ الطلب التشخيصي عبر API المعتمد
- توجيه طلب آمن وموثق بـ Bearer Token إلى المسار:
  `POST https://alrafeerouter.zone.id/api/v1/routers/test-connection`
- مع تمرير المعطيات التشخيصية التالية دون حفظها في أي سجلات غير مشفرة:
  ```json
  {
    "host": "<ROUTER_PUBLIC_IP_OR_AUTHORIZED_VPN_IP>",
    "port": 8729,
    "username": "jalsah_tester",
    "password": "<STRONG_TEST_PASSWORD>",
    "connectionMethod": "ROUTEROS_API_SSL",
    "certificateFingerprint": "<OPTIONAL_64_HEX_SHA256_FINGERPRINT>"
  }
  ```

#### المرحلة الثالثة: معايير النجاح (Success Criteria)
يعتبر الاختبار ناجحاً حصراً إذا تحققت جميع الشروط التالية:
1. استجابة الخادم السحابي برمز حالة HTTP `200 OK`.
2. حقل `success: true` في استجابة JSON.
3. استرجاع بيانات `RouterInfo` الكاملة:
   - `identity`: اسم الراوتر المعتمد.
   - `version`: إصدار RouterOS الفعلي (مثل `RouterOS v7.12`).
   - `boardName` / `model`: موديل الجهاز الفعلي.
   - `cpuLoad`: نسبة تشغيل المعالج.
   - `uptimeSeconds`: زمن التشغيل المحسوب بالثواني.
4. إغلاق المقبس فوراً بعد انتهاء القراءة وعدم بقاء أي قناة اتصال مفتوحة في السيرفر أو الراوتر.
5. عدم إحداث أي كتابة أو تغيير في قاعدة البيانات أو إعدادات الراوتر.

#### المرحلة الرابعة: معايير الفشل وطرق المعالجة (Failure Criteria & Troubleshooting)
- **`SSRF_BLOCKED`**: يشير العنوان إلى نطاق محلي خاص أو خطر. (الحل: استخدام عنوان عام أو نفق VPN مصرح به).
- **`AUTHENTICATION_FAILED`**: فشل تسجيل الدخول. (الحل: مراجعة اسم المستخدم وكلمة المرور وصلاحية الحساب).
- **`PERMISSION_DENIED`**: صلاحيات منقوصة. (الحل: التأكد من منح سياسات `api`, `read`, `test` للمستخدم).
- **`TLS_FINGERPRINT_MISMATCH`**: البصمة المدخلة لا تطابق شهادة الجهاز. (الحل: إعادة استخراج بصمة SHA-256 الصحيحة).
- **`TIMEOUT`**: انتهاء المهلة الزمنية دون وصول استجابة. (الحل: فحص جدار الحماية ومسار التوجيه وفتح المنفذ).
- **`CONNECTION_REFUSED`**: المنفذ مغلق في الراوتر أو لم يتم تفعيل خدمة `api-ssl`.

### 8. منهجية تنقيح السجلات وحماية السرية (Log Redaction & Confidentiality)
1. **تجريد السجلات (Sanitization)**: تضمن المنظومة برمجياً استبدال أي كلمات مرور أو مفاتيح تشفير أو توكنات بالقيمة `***` في سجلات التشغيل وواجهات الأخطاء.
2. **سجلات التدقيق (Audit Logging)**: تسجيل هوية المشغل وتوقيت الفحص والعنوان الهدف فقط دون تسجيل كلمات المرور.
3. **حذف مستخدم الاختبار فور الانتهاء**: فور انتهاء فحص التأهيل الميداني، يُنصح بتعطيل أو إزالة مستخدم الاختبار:
   ```routeros
   /user remove [find name="jalsah_tester"]
   ```

### 9. توضيح معماري: دعم الراوتر القريب من الهاتف (Near-Router vs Remote-Router Architecture)
- **الوضع الحالي المثبت بالكود**: المسار البرمجي المطبق حالياً يعتمد نموذج **(Remote Cloud-to-Router)**؛ حيث يتولى الخادم السحابي (`https://alrafeerouter.zone.id`) الاتصال مباشرة بعنوان الراوتر عبر الإنترنت أو شبكة VPN.
- **الراوتر القريب من الهاتف (Near Router)**:
  - إذا كان الراوتر موجوداً في نفس المكان مع هاتف المشغّل (متصلان بشبكة Wi-Fi محلية واحدة)، فإن خادم السحابة لا يستطيع رؤية عنوان الراوتر الداخلي (`192.168.88.1`).
  - دعم هذا السيناريو يتطلب معمارية مختلفة تماماً (تطبيق الهاتف Flutter يعمل كوسيط محلي Direct Client / Local Relay يتصل بالراوتر محلياً ثم يرسل التقارير للسحابة).
  - **هذا المسار المحلي غير مثبت حالياً في الأكواد ولم يتم تصميمه أو اختباره في المستودع الحالي**؛ لذا يقتصر التركيز الحالي على المسار البعيد المصرح به.
